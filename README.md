# 建筑规范结构化知识库（Building Code Knowledge Base）

把中文工程建设标准（国标 GB / 行标 JGJ 等）从 PDF/OCR 文本，**转成机器可读、可被设计软件与审查流程直接消费的 YAML 结构化数据**：条文编号、适用条件与例外、数值阈值、查表逻辑、强条与废止状态、IFC 对象映射、可执行规则。

当前开源 **6 本**标准（均为 v2.2 schema、机器门禁全 0）：GB 50222 / GB 55031 为深度复核样板（适用性 100% 回填）；GB 55024 / GB 55019 / GB 55036 / GB 55032 为通用规范家族扩展，适用性回填进行中（详见 §4）。

本仓库不止是一份数据集，而是一条**从标准原文到 IFC 模型可执行约束的全链条方法**：标准采集 → 条文结构化（Schema v2.2）→ 多层质量门禁 → IFC 模型绑定（Schema v2.3）→ 正反例回归验证 → 开源发布。方法体系、实证数据与设计取舍已成文：

* 📄 [工程建设标准条文结构化表示与 IFC 模型机器可执行绑定的全链条方法（公开版）](docs/工程建设标准条文结构化与IFC模型机器可执行绑定的全链条方法（公开版）.md) —— 全链条方法论：六层框架、Schema v2.2/v2.3、IDS 双轨、GB 50222 全书绑定实证与黄金样本回归（33 本标准 / 6636 条条文工程实践；引言与文献综述部分未收录）

方法论的落地细节见 [§7 全链条方法体系](#7-全链条方法体系与-ifc-绑定层)。

## 1. 为什么做这件事

工程设计行业信息化程度整体偏低，规范校验长期依赖人工完成，而代价最高的一类错误往往不是计算失误，而是规范读漏、读错。一份建筑总说明里散落着数十条引用规范，条文冲突、版本错配、图纸与规范不符等问题，常到施工图审查甚至现场返工才暴露，造成工期与成本损失。

这类问题在行业内十分常见：比如误用已废止的规范、跨专业条文要求矛盾、图纸标注与规范条文不一致等，人工逐条核对极易遗漏。

要从根源解决问题，核心是让规范的形态从「给人读的PDF」转向「给程序读的结构化数据」。本仓库就是把每条规范拆解为可被程序识别判定的最小单元，实现自动校验，将错误拦截在设计前期：

| 需求             | 结构化之后能做到                                                                                              |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| 设计说明里的引用条文是否齐全 | 每条带 `standard_code` + `clause_no`，可精确比对清单                                                             |
| 这条规定对我这个部位适不适用 | `applicability.scope` / `conditions` / `exceptions` 三元组                                               |
| 我的取值达标了吗       | `parameters[].min_value/max_value/unit`                                                               |
| 该查哪张表          | `tables[].headers/rows`（六册共 10 张表 92 行已结构化）                                                            |
| 是不是强条 / 有没有被废止 | `constraint.is_mandatory_clause` + `is_abolished` + `superseded_by`                                   |
| 能不能进 BIM 审查    | `related_objects.component_types` 映射到 IFC 实体；**宏观章节（术语/总则/基本规定/分类分级/分部验收）强制置空**；GB 50222-2017 已按 [`ifc-binding/`](ifc-binding/README.md) 精修到「IFC 实体 + `PredefinedType` + 空间上下文」，其余五册仍为宽匹配（见路线图） |
| 能不能直接被规则引擎跑    | `executable_rules`（when → then）                                                                       |

## 3. 数据结构速览

单份 YAML 由三层组成：`standard`（整本元数据）、`clauses`（逐条条文）、`executable_rules`（可判定规则）。完整字段定义与书写规约见 [`schema/SCHEMA_v2.2.yaml`](schema/SCHEMA_v2.2.yaml)。

```yaml
standard:                # 整本：编号、名称、实施/废止日期、强条数、相关规范、schema 版本
  code: GB 50222-2017
  clauses: [...]         # 条文 id 清单
clauses:
  - id: GB 50222-2017#3.0.4
    clause_no: 3.0.4
    chapter: 3 装修材料的分类和分级
    text: 安装在金属龙骨上燃烧性能达到B1级的纸面石膏板、矿棉吸声板，可作为A级装修材料使用。
    is_abolished: false
    superseded_by: null
    applicability:       # 「对谁有效」——主体 / 条件 / 排除
      scope: 安装在金属龙骨上的纸面石膏板、矿棉吸声板
      conditions: [燃烧性能达到 B1 级]
      exceptions: []
    constraint:          # 「多强」——严格等级 × 极性 + 是否强条 + 依据
      strictness: 可/may            # 必须/hard · 应/shall · 宜/should · 可/may · 无/none
      polarity: 正面/required       # 正面/required · 反面/prohibited · 正反并存/mixed · 无/null
      modal_words: [可]             # 证据：原文语气词全集
      modal_words_primary: [可]     # 定级主词
      is_mandatory_clause: false
      constraint_items: []          # 仅 mixed 时填充：条内按分句细化拆分
    parameters:          # 「到什么程度」——五字段统一签名
      - name: 纸面石膏板/矿棉吸声板燃烧性能等级
        unit: null
        condition: 安装在金属龙骨上
        min_value: null
        max_value: null
    tables: []           # 查表类条款：结构化 headers + rows
    references: []       # 跨标准引用 + 处置状态（resolved / unresolved）
    related_objects:     # IFC 实体与活动类型映射
      component_types: []                       # 宏观章节（术语/总则/基本规定/分类分级…）必须为空
      activity_types: [内部装修防火设计]          # 宏观条文仍归属本册业务活动，不受影响
executable_rules:        # 面向规则引擎：when 条件数组 → then 结论
  - rule_id: R_GB50222_3_0_4_board_grade
    when: ["material IN ['纸面石膏板','矿棉吸声板']", "fire_performance == 'B1'", "install == '金属龙骨'"]
    then: { result_grade: A }
```

**几条立规矩的经验**（都是踩过坑才定下来的）：

* **参数必须五字段齐名**：`name / unit / condition / min_value / max_value`，缺 unit 也要显式 `null`。这是所有下游脚本的字段签名。

* **「除 X 外」不写进** **`exceptions`**：那是 SQL 式排除思维。范围限定应并入 `scope`（限定主体）或 `conditions`（条件分支），`exceptions` 只放被排除对象本身。

* **等级型/枚举型条款不是阈值约束**。像「B1 级可视同 A 级」这种等效规则，`>=` 数值比较是错的——参数层用 `condition` + `_v21_param_note` 说明，真正的换算逻辑放 `executable_rules`。

* **不要发明新字段名**。`operator` / `value` 这类自定义键不会被任何脚本识别，也不会进规则镜像。

## 7. 全链条方法体系与 IFC 绑定层

本节是论文 [《工程建设标准条文结构化表示与 IFC 模型机器可执行绑定的全链条方法》](docs/工程建设标准条文结构化与IFC模型机器可执行绑定的全链条方法（公开版）.md) 的方法论提要，也解释了本仓库各目录之间的因果链。

### 7.1 六层框架

| 层 | 做什么 | 本仓库对应 |
| --- | --- | --- |
| ① 标准采集 | 从标准全文公开系统分页抓取，PDF 文本层 / OCR 双通道建立逐条可回源的文本基线 | 私有工作区（源基线不外发） |
| ② 条文结构化 | 按 Schema v2.2 把条文解析为结构化 YAML，形成知识库正本 | [`schema/`](schema/) + [`standards/`](standards/) |
| ③ 质量门禁 | 模式 / 语气 / 文本缺陷 / 副本一致性四层审计，归零方可进入下游 | [`tools/`](tools/)（可独立复跑） |
| ④ IFC 绑定 | 按 Schema v2.3 建立「条文 → IFC4 实体 + PredefinedType + 空间上下文」绑定，编译为可执行规则 | [`ifc-binding/`](ifc-binding/README.md) |
| ⑤ 验证 | 黄金样本正反例回归、编译一致性比对、工厂造模型实测 | [`ifc-binding/samples/`](ifc-binding/samples)、[`ifc-binding/scenarios/`](ifc-binding/scenarios) |
| ⑥ 发布 | 正本 / 副本 / 开源仓库三轨同步，阅读视图与工具链随库发布 | 本仓库 |

**两条贯穿全程的原则**：

* **文本唯一权威**——`text` 字段是条文语义的最高裁决者。结构化字段与原文冲突时以文本为准，并触发审计（v2.2 语气审计内含「由 `text` 重推导」一致性校验）。
* **单一事实源**——属性值只存在于 `parameters[]`，绑定层与规则只引用参数标识（`parameter_ref`），杜绝同一数值多处存值后漂移。

### 7.2 为什么单维语气不够用（v2.2 的核心判据）

条文的强制程度是**两个正交维度**：强度梯度（必须/应/宜/可）与约束方向（正面下界 / 反面上界）。v2.2 用 `strictness` × `polarity` 二维刻画，跨档条文按「取严」定强度、极性独立判定。

关键判例是**边界语义不等于禁止**：「不得小于」「不应低于」虽含否定词，语义却是正面下界约束，方向由参数的 `min_value` / `max_value` 承载。判据形式化为「否定词 + 紧邻边界动词（间隔 ≤ 3 字且无实义动词）→ `polarity` 判正面」。漏了这条，会把大量下界要求误标成禁止项，直接反判合规结论。

### 7.3 九级绑定层级与七类模板（v2.3）

`binding_level` 取 `macro / site / building / storey / space / system / element / process / document` 九级之一。**`macro` / `process` / `document` 三级不得携带构件绑定**（审计强制），从模型上杜绝「宏观条文挂构件」的语义错挂。

为保证批量生产的一致性，绑定书写收敛为七个模板：

| 模板 | 适用条文类型 | 例 |
| --- | --- | --- |
| **T1 部位值域** | 单一部位的材料/性能值域 | 「顶棚装修材料不应低于 A 级」→ `IfcCovering.CEILING` + 燃烧性能值域 |
| **T1_table 表格型部位值域** | 场所 × 部位二维表展开 | GB 50222 的场所-部位矩阵（同列同值行合并为一条绑定） |
| **T2 属性存在性** | 「应设置…」类存在性要求 | 「应设保温层」 |
| **T3 系统成员齐备** | 跨对象编组 `has_all` | 防雷系统组成完整性 |
| **T4 系统/设备属性值域** | 数值 + 单位比较 | 设备参数阈值 |
| **T5 过程活动** | 检验、验收类条文 | 绑到 `process` 而非构件 |
| **T6 宏观/场地** | 无构件落点的宏观要求 | 空绑定，降级人工复核 |

T1_table 暴露出一类典型陷阱：**带条件行**（按建筑规模分档）在当前 IFC 空间分类能力下无法无损展开，强行按原子房间名拆分反而会与面积分档语义冲突、误伤合规件。工程处理是只展开无条件行，带条件行整条降级为专家复核标记——**宁可降级，不做伪绑定**。

### 7.4 IDS 双轨执行

绑定产物不硬塞进单一执行通道，按表达能力分轨：

| 约束类型 | 执行轨 | 说明 |
| --- | --- | --- |
| 单对象属性值域、枚举、存在性、禁止值 | **IDS 轨** | 导出标准 IDS（`in` / `exists` / `gt·gte·lt·lte` 经 `xs:restriction` / `not_in` 经 `cardinality=prohibited`），交任意 IDS 兼容检查器执行 |
| 空间 / 空间组上下文、跨对象编组、材料级分类回退、几何推导、过程类条文 | **自研引擎轨** | 基于 IfcOpenShell 的规则引擎 |

**实测依据**：IDS 能覆盖「单对象属性值域」类约束，但对空间上下文、跨对象编组与几何推导无能为力——这就是分轨的直接原因。空间限定不进 IDS 导出时，检查口径会从「限定空间」放大为「全楼」，即导出结果比条文更严（宁严勿宽，但使用者须知情，见 §7.7）。

### 7.5 绑定层审计与「死名」治理

[`ifc-binding/tools/audit_binding_v23.py`](ifc-binding/tools/audit_binding_v23.py) 共 15 项检查，分五类：实体与枚举合法性；语义错配与单一事实源（**燃烧性能 ↔ 耐火极限混绑**、字面值入侵、孤儿引用、层级错挂）；空间收窄丢失的三分支判定；册级比例控制（单一实体组合占比、预定义类型使用率）；编译一致性（落盘规则与源数据现场重编译逐条比对）。审计器自带 **18 项自检，全部通过**——先证明审计器本身没瞎，再用它审数据。

**「死名」治理**：宽匹配映射会产生 IFC4 中根本不存在的实体名。已确认三个高发死名——`IfcCeiling`（正解 `IfcCovering.CEILING`）、`IfcFloor`（正解 `IfcSlab.FLOOR`）、`IfcEntrance`（正解 `IfcDoor`）——收录进映射词表的 `forbidden` 清单并由审计器拦截，全库累计清理 **690 处**（5 本标准 685 处 + 模板注册表 5 处），残留清零。教训一句话：**映射词表必须同时定义「可用」与「禁用」，只定义前者必然漏检**。

### 7.7 已知局限

1. **条件行承载力**——按建筑规模/性质分档的条文（如分档表格）无法在当前 IFC 空间分类下无损展开，只能降级人工复核。需扩建筑分类 zone 词表，属词表工程而非模型缺陷。
2. **IDS 轨口径收窄**——空间限定不进 IDS 时，检查口径由「限定空间」放大为「全楼」，导出结果比条文更严。
3. **文本命中率须分辨归因**——全库条文与源基线逐字命中率 70.3%（4664/6636），未命中部分主要是源扫描件无文本层与 OCR 噪声。评价质量必须区分「结构化缺陷」与「源基线缺陷」两类口径，否则会系统性低估结构化成果。
4. **规则表达力边界**——少量 v2.2 遗留规则含「升降级」等 v2.3 暂无法表达的语义，当前保留不删，待规则 DSL 扩展后迁移。

## 8. 生成方式与工具链

这套数据既不是纯手写，也不是纯自动生成，走的是\*\*「LLM 辅助抽取 → 机器审计 → 人工精校」\*\*三段式：

| 阶段    | 承担者   | 做什么                                                         |
| ----- | ----- | ----------------------------------------------------------- |
| 初筛与抽取 | 大语言模型 | 从 PDF/OCR 文本中识别条文边界、情态词、数值参数、表格结构，产出 YAML 草稿                |
| 机器审计  | 审计脚本  | 按 `SCHEMA_v2.2` 与 V1–V9 规则逐条扫描，把问题收敛成可机检清单                  |
| 人工精校  | 人     | 标准 PDF 按 120 DPI 全本渲染后逐页视觉比对，处理机器判不了的部分（语义归属、等级型条款、误抽与幽灵条文） |

本项目的绝大部分内容，是在 **WorkBuddy** 与 **Trae** 两个 Agent 中协作互审完成的，过程中使用了 **QWEN3.7、KIMI K3、GLM5.3** 等大模型。

这里有一点值得强调：**这套数据模型是模型无关的**。无论换用哪个模型参与抽取，产出都必须通过同一份 `schema/SCHEMA_v2.2.yaml` 和同一套审计脚本——结构由模式约束，而不是由某个模型的输出习惯决定。这正是我们敢于让多个模型参与、并把结果整合进同一套数据的前提：模型负责提效，模式和审计负责收敛质量。
